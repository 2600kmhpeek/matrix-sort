# Сравнительный анализ методов тестирования

Документ подготовлен по результатам ЛР №4. Для каждого метода указано, как он
применялся в проекте «МатрСорт-16».

## 1. Методы «чёрного ящика»

| Метод | Суть | Преимущества | Недостатки | Применение в проекте |
|-------|------|--------------|------------|----------------------|
| Эквивалентное разбиение | входные данные делятся на классы, из каждого берётся представитель | резко сокращает число тестов; не требует знания кода | можно пропустить дефект на границе классов | проверка размерности, элементов матрицы, кодов ответа HTTP |
| Анализ граничных значений | проверяются значения на границах и рядом с ними | находит типичные ошибки сравнений и ограничений | требует знать границы; не покрывает середину класса | 1 × 1, 100 × 100, 10 100 элементов, `retries = 0`, версии `1.9`/`2.0`, 1000/1001 элемент вывода |
| Анализ причинно-следственных связей | строится логическая связь «вход → выход» | хорошо формализует сложные правила | трудоёмок при большом числе условий | не применялся: правила валидации простые |
| Предположение об ошибке | опытный тестировщик предугадывает слабые места | дёшево находит дефекты, пропущенные формальными методами | зависит от опыта; не систематичен | проверка `bool`, `None`, `nan`/`inf`, не-JSON ответа, неверной структуры ответа |

## 2. Методы «белого ящика»

| Критерий | Что требует | Преимущества | Недостатки | Применение в проекте |
|----------|-------------|--------------|------------|----------------------|
| Покрытие операторов | каждая строка выполнена | простой и наглядный | не гарантирует проверку всех ветвей | базовый уровень, покрытие 90 % |
| Покрытие решений | каждая ветвь `if/else` пройдена в обе стороны | находит ошибки в ветвлениях | не проверяет комбинации условий внутри решения | все ветви `validate_matrix`, `input_size`, `_parse_response`, цикла повторов |
| Покрытие условий | каждое простое условие истинно и ложно | глубже покрытия решений | число тестов растёт | отдельно проверены части `or`-условий (`rows`, `row`, элемент) |
| Комбинаторное покрытие условий | все комбинации условий в решении | максимальная полнота | экспоненциальный рост числа тестов | для проверки элемента: `bool`, не число, не конечное число, корректное число |

## 3. Уровни тестирования

| Уровень | Преимущества | Недостатки | Применение |
|---------|--------------|------------|------------|
| Модульное | быстро локализует дефект, дешёвое | не проверяет взаимодействие | `test_matrix_sort.py`, `test_service.py`, `test_client.py`, `test_integrated_app.py` |
| Интеграционное | проверяет контракты и передачу данных | сложнее и медленнее, нужен запуск сервиса | `test_integration.py` (19 проверок по HTTP) |
| Системное | проверяет сценарий целиком | дорого автоматизировать | ручной запуск `integrated_app` |
| Регрессионное | не даёт вернуть старые дефекты | требует поддержки при изменении кода | `test_regression.py`, отдельное задание CI |

## 4. Инструменты

| Инструмент | Назначение | Оценка |
|------------|------------|--------|
| pytest | запуск тестов, параметризация, фикстуры | удобен, минимум шаблонного кода, богатые отчёты |
| pytest-cov | покрытие операторов и ветвей | встроен в отчёт, поддерживает порог `--cov-fail-under` |
| unittest.mock / monkeypatch | подмена HTTP и ввода | позволяют тестировать без сети и ручного ввода |
| flake8 | инспекция стиля | быстрый, легко встраивается в CI |
| GitHub Actions | CI | бесплатен для открытых проектов, нагляден |

## 5. Рекомендации

1. Для небольших проектов достаточно сочетания эквивалентного разбиения,
   граничных значений и покрытия решений — это даёт максимум эффекта при
   умеренном числе тестов.
2. Комбинаторное покрытие стоит применять точечно, к критичным решениям:
   полный перебор быстро становится неоправданно дорогим.
3. Отказы внешних компонентов нужно проверять отдельно (таймауты, неверный
   JSON, неверная структура ответа), иначе они остаются вне покрытия.
4. Регрессионные тесты должны создаваться сразу при исправлении дефекта:
   это единственный способ гарантировать, что дефект не вернётся.
5. Порог покрытия в CI следует ставить выше целевого по заданию (в проекте —
   80 % при цели 70 %), чтобы покрытие не снижалось со временем.

## 6. Вывод

Для «МатрСорт-16» оптимальным оказался набор: эквивалентное разбиение +
граничные значения (чёрный ящик) и покрытие решений/условий (белый ящик) с
обязательными регрессионными тестами. Он выявил два реальных дефекта, дал
покрытие 90 % и полный прогон менее чем за секунду.
